# Smart Garden — Sensor Data Architecture

**Version:** v0.3
**Jira:** SG-16
**Status:** Draft

## 1. Objective

Design a reliable and extensible data pipeline for collecting
environmental measurements from physical sensors, transmitting
them through ESP32, storing them in PostgreSQL, and exposing
them through FastAPI.

The initial implementation targets one capacitive soil
moisture sensor connected to an ESP32 DevKitC.

## 2. Component Responsibilities

| Component       | Responsibility                                               |
| --------------- | ------------------------------------------------------------ |
| Moisture sensor | Produces an analog signal related to soil moisture           |
| ESP32 DevKitC   | Reads ADC values and transmits measurements over Wi-Fi       |
| FastAPI         | Authenticates, validates and processes incoming measurements |
| PostgreSQL      | Stores measurement history and sensor metadata               |
| GardenPi        | Hosts FastAPI and PostgreSQL                                 |

## 3. Communication Architecture

**Selected protocol:** HTTP/JSON over Wi-Fi.

Initial data flow:

1. The moisture sensor produces an analog signal.
2. ESP32 converts the signal into a raw ADC reading.
3. ESP32 sends an HTTP POST request to FastAPI.
4. FastAPI authenticates the device and validates the payload.
5. FastAPI resolves the sensor's current pot assignment.
6. PostgreSQL persists the measurement.
7. FastAPI acknowledges successful storage.
8. Clients retrieve measurements using a GET endpoint.

HTTP was selected for simplicity and direct FastAPI integration.

MQTT and wired communication remain possible future alternatives.

### Measurement Frequency

The initial target is approximately one measurement per hour,
consistent with ADR-0001.

The interval must be configurable in ESP32 firmware.

The final interval will be determined through sensor testing,
measurement stability and practical monitoring requirements.

## 4. Design Principles

- Devices, sensors, pots and plants have separate identities.
- Raw sensor measurements are preserved.
- Sensor-to-pot assignments are managed server-side.
- Historical measurements retain their original pot association.
- Repeated delivery of the same measurement must not create duplicates.
- Network and database failures must be handled explicitly.
- Sensor ingestion must remain independent of the physical transport where practical.

## 5. Initial PostgreSQL Data Model

The initial schema contains four entities:

### devices

- `id`: Internal primary key
- `device_id`: Unique external identifier
- `name`: Human-readable device name

### pots

- `id`: Internal primary key
- `pot_id`: Unique external identifier
- `plant_name`: Optional plant description

### sensors

- `id`: Internal primary key
- `sensor_id`: Unique external identifier
- `device_id`: Foreign key referencing devices
- `pot_id`: Nullable foreign key referencing the currently assigned pot
- `metric`: Measurement type

### measurements

- `id`: Internal primary key
- `measurement_id`: Unique observation identifier generated by ESP32
- `sensor_id`: Foreign key referencing sensors
- `pot_id`: Nullable foreign key preserving the pot association at ingestion
- `value`: Raw numerical measurement
- `unit`: Measurement unit, e.g. adc_raw
- `recorded_at`: Server-generated timestamp with timezone
- `device_id`: Foreign key referencing the device that originally submitted the measurement
- `metric`: Measurement type preserved at ingestion (e.g., soil_moisture)

## 6. Data Integrity Rules

- Device and sensor identifiers must be unique.
- Each sensor belongs to one registered device.
- Measurements reference registered sensors.
- Sensor-to-pot assignments are resolved server-side.
- Historical measurement associations are immutable.
- Duplicate measurement identifiers must not create duplicate records.
- Unsupported metric/unit combinations must be rejected.
- Raw ADC measurements are preserved without assuming calibrated percentages.
- Measurement identifiers must remain unique across ESP32 restarts; a UUID-based approach is preferred.
- Each measurement preserves the identity of the submitting device.
- Historical device and pot associations must remain unchanged after sensor reassignment.
- Identical retries must be evaluated against the original stored measurement, not only the sensor's current assignment.
- Device authentication and authorization are required before acknowledging historical retries.

## 7. REST API Contracts

### POST /api/garden/measurements

Receives a measurement from an authenticated ESP32 device.

Example request:

```json
{
  "measurement_id": "esp32-01-000001",
  "device_id": "esp32-01",
  "sensor_id": "soil-01",
  "metric": "soil_moisture",
  "value": 2450,
  "unit": "adc_raw"
}
```

The API will:

1. Authenticate the device.
2. Validate the payload and supported metric/unit combination.
3. Verify that the sensor belongs to the authenticated device.
4. Resolve the sensor's current pot assignment.
5. Record the server-side timestamp.
6. Persist the measurement transactionally in PostgreSQL.
7. Return HTTP 201 after successful insertion.

Example response:

```json
{
  "id": 1042,
  "status": "stored",
  "recorded_at": "2026-11-04T10:30:00Z"
}
```

### GET /api/garden/measurements

Retrieves stored measurements, ordered newest first.

Example:

`GET /api/garden/measurements?sensor_id=soil-01&limit=10`

The default and maximum result limits will be defined
during implementation.

Historical records retain the pot association captured
when the measurement was stored.

## 8. Authentication and Network Security

- Each ESP32 device uses a unique API key.
- API keys are supplied in an HTTP request header.
- Credentials are never committed to Git.
- Ingestion is restricted to the trusted local network.
- Device identity must be verified against its credential.
- TLS or an equivalent protected transport is required
  before communicating over untrusted networks.
- The current localhost-only FastAPI service must not
  be exposed without a separate network security review.

## 9. Reliability and Failure Handling

- ESP32 uses bounded retries for temporary failures.
- Pending readings may be held in a limited RAM queue.
- RAM buffering does not survive device power loss.
- Retries reuse the original measurement_id.
- PostgreSQL enforces measurement identifier uniqueness.
- Identical duplicate requests are acknowledged without
  creating another database record.
- Conflicting payloads using an existing measurement_id
  are rejected with HTTP 409.
- Invalid requests are rejected without persistence.
- Temporary database outages return HTTP 503.
- Persistent buffering and guaranteed delivery are deferred.

## 10. HTTP Response Codes

| Status | Meaning                                      |
| ------ | -------------------------------------------- |
| 201    | Measurement successfully created             |
| 200    | Existing identical measurement acknowledged  |
| 400    | Unsupported metric/unit combination          |
| 401    | Missing or invalid device credentials        |
| 409    | Conflicting duplicate measurement identifier |
| 422    | Invalid request structure or field values    |
| 503    | Database temporarily unavailable             |
| 500    | Unexpected internal server error             |
